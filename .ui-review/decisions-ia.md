## 决策 1 —— IA-1：侧栏「同壳模块」与「独立路由页」在视觉上完全无法区分

### 实测事实

侧栏 8 项的渲染结果**逐项完全一致**：

| key | 标签 | kind | 高度 | 字号 | 文字色 | 图标色 | 子元素数 | 外链标记 |
|---|---|---|---|---|---|---|---|---|
| overview | 概览 | `route` | 40px | 14px | rgb(110,110,115) | rgb(110,110,115) | 2 | 无 |
| bookmarks | 收藏夹 | `module` | 40px | 14px | rgb(29,29,31)* | rgb(201,37,106)* | 2 | 无 |
| notes | 便签 | `module` | 40px | 14px | rgb(110,110,115) | rgb(110,110,115) | 2 | 无 |
| files | 云盘 | `module` | 40px | 14px | rgb(110,110,115) | rgb(110,110,115) | 2 | 无 |
| vault | 密码库 | `module` | 40px | 14px | rgb(110,110,115) | rgb(110,110,115) | 2 | 无 |
| music | 音乐 | `route` | 40px | 14px | rgb(110,110,115) | rgb(110,110,115) | 2 | 无 |
| recycle | 回收站 | `route` | 40px | 14px | rgb(110,110,115) | rgb(110,110,115) | 2 | 无 |
| extension | 下载中心 | `route` | 40px | 14px | rgb(110,110,115) | rgb(110,110,115) | 2 | 无 |

\* 收藏夹为当前激活项，色差来自激活态而非 kind。

**根因**：`jnclub-web/src/shared/layout/navConfig.ts:16` 定义了 `kind: 'module' | 'route'`，注释也写明「module：主壳内 4 大模块（emit module-change）；route：独立路由（router.push）」，但 `jnclub-web/src/shared/layout/NavItem.vue` **完全不读这个字段**（模板只有 `@click="$emit('click')"`）。kind 是只写不读的元数据。

**点击后的实际差异**（实测）：

| 点击项 | 结果 URL | 顶栏变成 |
|---|---|---|
| 便签（module） | `/jnclub/?module=notes&dir=21` | 面包屑条（AppHeader） |
| 概览（route） | `/jnclub/overview` | 大标题条（JPageHeader） |

**关键缓解事实**：第二批 P0-1 已让两套页头的**数值**完全对齐 —— 同为 `--header-height` 60px 高、同一条通栏 `1px solid var(--border)` 底线、标题 18px/700。所以「跳变感」已大幅削弱；剩下的差异是**结构**（面包屑 vs 大标题），不是尺寸。

### 问题本质

用户在点击前无法预期：这一下是「在主壳里换个模块」（顶栏保持面包屑、左栏目录树还在）还是「离开主壳去另一个页面」（顶栏换成大标题）。两种操作的心智模型不同，但入口长得一模一样。

### 选项

**A. 维持现状，记录为已知取舍（推荐）**
- 理由：P0-1 之后两套页头已视觉同构，跳变感已削弱；加标记等于「用新视觉元素解释架构分层」，而架构分层是开发者视角，不是用户视角。用户真正关心的是「我要去便签」，而不是「便签是 module 还是 route」。
- 成本：0。需在报告里把 IA-1 状态改为「经复核判定为可接受的设计取舍」。

**B. 侧栏分组：用既有分隔线把 module 组与 route 组分开**
- 形态：`概览` ｜ `收藏夹 便签 云盘 密码库` ｜ `音乐 回收站 下载中心`（两条分隔线）。
- 优点：零新视觉元素（分隔线是侧栏既有语言）；分组本身即暗示「同一组内行为一致」。
- 代价：必须重排 `DEFAULT_ORDER`（当前是 `overview, bookmarks, notes, files, vault, music, recycle, extension`，module 与 route 交错）。**会与用户已有的自定义顺序偏好（localStorage `nav.order`）冲突**，需要迁移策略或放弃用户自定义顺序。

**C. 给 route 项加细微标记（如 hover 时才出现的小箭头）**
- 优点：改动小。
- 代价：引入新的视觉语汇；且「小箭头」在中文语境里通常表示「外链/新窗口」，语义不准。

### 我的判断

推荐 **A**。核心理由：IA-1 是「架构差异泄漏到 UI」的典型症状，而正确的解法通常是**消除架构差异**（让 route 项也进主壳）或**接受它**（用户不需要知道）。加视觉标记是最差的中间态 —— 它把开发者的分层概念教给用户，用户学到的知识却没有任何可操作的用途（无论哪种点击，他都是「去便签」）。而「消除架构差异」对音乐（独立前端）和下载中心（插件页）不现实。

若你更看重「可预期性」，选 **B**（分组），但要接受重排顺序。

## 决策 2 —— IA-2：面包屑首项「JNClub」与第二项点击效果完全相同

### 实测事实

`jnclub-web/src/shared/layout/AppHeader.vue:252-260`：

```html
<NBreadcrumb class="jnclub-breadcrumb">
  <NBreadcrumbItem @click="handleBreadcrumbRoot">JNClub</NBreadcrumbItem>
  <NBreadcrumbItem @click="handleBreadcrumbRoot">{{ 模块名 }}</NBreadcrumbItem>
  <NBreadcrumbItem v-if="breadcrumbCurrent !== '全部'" class="breadcrumb-current">
    {{ breadcrumbCurrent }}
  </NBreadcrumbItem>
</NBreadcrumb>
```

**前两项绑的是同一个 handler**。实测（便签页 dir=21）：

| 操作 | URL 变化 | `breadcrumbCurrent` |
|---|---|---|
| 点「JNClub」 | 不变（`?module=notes&dir=21`） | 变为 `null`（第三项消失） |
| 点「便签」 | 不变（`?module=notes&dir=21`） | 变为 `null`（第三项消失） |

**两项效果逐位相同**，都是 `selectedDirectoryId = null` + 退出批量模式（回到「全部」）。

DOM 语义实测：两项都是 `<span class="n-breadcrumb-item__link">`，`cursor: none`（不可点击的视觉暗示），文字色 rgb(110,110,115)、字重 400；第三项 rgb(81,81,84)、字重 600。

**移动端已有隐藏逻辑**（说明团队已意识到首项冗余）：
- `AppHeader.vue:669-671`：`@media (max-width: 767px)` 下 `:first-child { display: none }`，注释写「移动端不需要品牌根链接：目录按钮已能唤起完整目录树，宽度让给当前路径」
- `AppHeader.vue:719`：`@media (max-width: 400px)` 下当存在第三项时连第二项也隐藏

**即：桌面端是唯一还显示这个冗余首项的地方。**

### 问题本质

面包屑的每一级应当代表一个**可回退的层级**。这里首项与第二项代表同一个层级（「全部」），只是文案不同。它不是「点击无去处」（实测点击有效果），而是**点击效果与下一项重复**，属于占位冗余。

### 选项

**A. 桌面端也隐藏首项「JNClub」（推荐）**
- 做法：把 `AppHeader.vue:669-671` 的移动端规则提到全局（或复制一份到桌面），同时删掉模板里的首项。
- 结果：面包屑变「便签 / 工作」（选中目录时）或「便签」（根目录时）。
- 理由：①与移动端一致，一套语言；②品牌名在侧栏 logo 区已有，顶栏重复；③首项本身无独立语义（与第二项同效），删掉不丢信息。
- 成本：模板删 1 行 + CSS 微调，极小。

**B. 首项改指向概览（`router.push('/overview')`）**
- 优点：给首项一个独立语义（「回到首页/概览」）。
- 缺点：「JNClub」这个文案指向「概览」不直观；概览已在侧栏首项，属重复入口。

**C. 首项与第二项合并为一项**
- 形态：面包屑只剩「便签 / 工作」，模板删掉整个首项，第二项保留（因为它是当前模块名，仍有定位价值）。
- 与 A 的实际结果相同，只是实现上更彻底（A 是 CSS 隐藏，C 是模板删除）。**推荐用 C 的实现方式**，避免留一个「永不显示的 DOM」。

### 我的判断

推荐 **A + C 合并**：模板删掉首项，面包屑从三项变两项。这是「用最少的信息表达最多层级」的标准做法。

## 决策 3 —— IA-4：搜索抽屉标题「命令面板」与实际主体不符

### 实测事实

抽屉标题实测为「命令面板」（`jnclub-web/src/modules/bookmark/components/SearchDrawer.vue:496` 的 `text="命令面板"`，用 `JGradientText` 渲染）。

抽屉的**完整结构**（实测 DOM）：

| 区域 | 类名 | 内容 | 何时显示 |
|---|---|---|---|
| 标题 | `.search-title` | 「命令面板」 | 常驻 |
| 输入框 | `.search-header input` | placeholder「搜索收藏 / 便签 / 文件 / 密码 / 音乐…」 | 常驻 |
| 最近搜索 | `.history-title` | 历史关键词 chip | 空输入 |
| 快捷操作 | `.cmd-subtitle` + `.cmd-list` | **12 项命令** | 空输入 |
| 最近打开 | — | 最近访问的条目 | 空输入 |
| 空态提示 | `.empty-title` (H3) | 「搜索收藏、便签、云盘、密码库和音乐」 | 空输入 |
| 搜索结果 | `.search-results` | 按类型分组的跨模块结果 | 有输入 |

唤起方式：`Ctrl/⌘ + K`。

### 问题本质

这是一个**混合体**：搜索优先（placeholder 与结果区都是搜索），空态回退到命令面板（12 项快捷操作 + 最近搜索 + 最近打开）。报告原文判断「标题『命令面板』但主体是跨模块搜索」是准确的。

但需要指出：行业里这个模式**就叫 Command Palette**（Raycast、VS Code、Linear 都用此名，且都能搜文件/条目）。所以「命令面板」不是错误命名，而是**沿用了行业术语**。真正的判断点是：JNClub 的用户群是否熟悉这个术语。

### 选项

**A. 改「搜索」（推荐）**
- 理由：与 placeholder、结果区一致；对不熟悉 Command Palette 概念的用户更直白；`Ctrl/⌘+K` 已是搜索的通用快捷键。
- 代价：抽屉里的 12 项快捷操作变得「名不副实」，但它们是空态回退内容，可接受。

**B. 改「搜索与命令」**
- 理由：忠实描述混合体。
- 代价：略长，且「命令」对普通用户仍是抽象词。

**C. 维持「命令面板」**
- 理由：符合行业惯例（Raycast / VS Code Command Palette）；项目里确实有命令列表。
- 代价：非开发者用户可能不理解。

**D. 改「全局搜索」**
- 理由：强调跨模块（收藏/便签/云盘/密码库/音乐）。
- 代价：与 A 差别不大，多两字。

### 我的判断

推荐 **A（「搜索」）**。理由：这是一个个人工作台而非开发者工具，用户群不预设熟悉 Command Palette 术语；且抽屉里搜索占主位（有输入时命令列表完全不显示）。

若你认为「命令面板」的定位是有意为之（未来会加更多命令），则选 **C** 并保持不变 —— 这也是完全合理的决定。

## 决策 4 —— IA-5：概览/回收站的「返回」按钮永远回到收藏夹

### 实测事实

`jnclub-web/src/shared/layout/OverviewLayout.vue:56` 与 `jnclub-web/src/modules/bookmark/layout/RecycleLayout.vue:72`：

```html
@back="router.push('/')"
```

按钮本身：`jnclub-web/src/shared/components/ui/JPageHeader.vue:60-69`，`title="返回"`、`aria-label="返回"`、图标 `ArrowLeft`。

**实测三个场景**：

| 场景 | 进入方式 | 点击「返回」后落到 |
|---|---|---|
| A | 便签页 → 概览 | `/jnclub/`（收藏夹）——**不是来时的便签** |
| B | 云盘页 → 回收站 | `/jnclub/`（收藏夹）——**不是来时的云盘** |
| C | 直接刷新打开概览 | `/jnclub/`（收藏夹） |

`router.push('/')` 解析为 `/jnclub/`，而主壳默认模块是收藏夹。

### 问题本质

这是一个**功能缺陷**，不只是 IA 问题。按钮的图标（左箭头）、`title`、`aria-label` 三者一致地承诺「返回上一页」，实际行为却是「跳到收藏夹」。用户从便签进概览想回去，会被送到收藏夹 —— 这是明确的预期违背。

### 选项

**A. 智能返回（推荐）**

```ts
const goBack = () => {
  // history.state.back 为 null 表示没有可返回的历史（如直接打开该 URL）
  if (router.options.history.state.back) router.back()
  else router.push('/')
}
```

- 理由：符合「返回」的字面语义与图标；直接打开时仍有个合理落点（收藏夹）。
- 成本：两处各改 1 行 + 加一个函数（可提取到 composable 共用）。
- 注意：`router.options.history.state.back` 是 Vue Router 4 的稳定 API。

**B. 直接 `router.back()`**
- 优点：最简。
- 缺点：无历史时点击无反应（用户以为按钮坏了）。

**C. 维持 `push('/')`，改按钮文案为「回到收藏夹」**
- 优点：文案与行为一致。
- 缺点：左箭头 + 「回到收藏夹」语义冲突；且用户仍无法回到来路。

**D. 记录来路**：进入概览/回收站时把来源模块存进 store，返回时恢复。
- 优点：最符合「返回」的直觉，即使跨刷新也有效。
- 缺点：需要处理「来源模块已被删除/无权限」等边界；实现复杂度明显高于 A。

### 我的判断

推荐 **A**。这是标准做法，成本极低，覆盖了「无历史」的边界情况。D 更完善但收益边际。

## 决策 5（技术债）—— 网格模式虚拟滚动 `itemHeight: 220` 虚高 32%

### 实测事实

`jnclub-web/src/modules/bookmark/components/CollectionGrid.vue:67` 与 `NoteGrid.vue:68` 均 `useVirtualList(rows, { itemHeight: 220, overscan: 2 })`。

- 实测卡片行高（`.virtual-row`，3 列网格）：**148.59px**（`148.59 = 卡片 132.59 + 行距 16`）
- `itemHeight: 220` 相对真实行高**虚高 71.4px（32%）**
- 后果：滚动时出现**可见跳变**。实测以每次 +40px 滚动采样，`scrollTop` 从 400 → 440 时，首行 `top` 从 -113.5 **突变为 +66.5**，内容瞬间跳动约 **180px**
- 对照：列表模式 `itemHeight: 64` vs 真实 58.9，偏差仅 5.1px，察觉不到
- 网格 `scrollHeight` 8800 = 40 行 × 220（120 条 / 3 列），占位正确，只是单行估值偏大

### 风险不对称（关键判据）

- **改小** → 若真实卡片比估值高（标题换行、标签多行），相邻行会**重叠**（负向、可见的破版）
- **不改** → 只是滚动时内容跳一下（正向、可容忍）

卡片高度实测：`132.59px`。但 `CollectionCard.vue` **无固定高度**，`.title-text` 也无 `line-clamp`，唯一高度变量是标签行数。压测数据每条只有 1 个标签，无法量出「多标签 + 标题换行」的上界（曾尝试注入多标签失败：mock 数据里 `.card-tags` 节点不存在）。

### 选项

**A. 维持 220（推荐）**
- 理由：风险不对称 —— 重叠是破版，跳变只是观感。且上界未测出，改小属赌博。

**B. 调小到 160 左右**
- 优点：消除大部分跳变。
- 风险：真实数据里标题换行 + 标签换行时可能重叠。需先用真实多标签数据量出上界。

**C. 动态测量行高（ResizeObserver）**
- 优点：彻底正确。
- 缺点：与 `useVirtualList` 的固定 `itemHeight` 模型冲突，需要自研或换库；成本远高于收益。

**D. 给卡片加固定高度（`min-height` + `line-clamp`）**
- 优点：让 220 这个值「名正言顺」；顺带让网格排列更整齐。
- 缺点：改变卡片视觉（标题截断、标签截断），属新的设计决策。

### 我的判断

推荐 **A**，并把「网格模式虚拟滚动跳变」记为已知限制。若你希望修，推荐先做 **D**（给卡片定高 + line-clamp），这样 itemHeight 才有一个**可保证的上界**，然后才能安全地把 220 调到接近真实值。B 单独做是赌博。

## 决策 6（技术债）—— 概览统计数值 24px 的字号层级

### 实测事实

`jnclub-web/src/shared/components/ui/JStatCard.vue:80-83` `.j-stat-value { font-size: var(--fs-5xl) }`（24px）、`font-weight: 800`。

报告 P1-8 原建议「提到 32px（`--fs-7xl`）」经实测**否决**：

1440px 下 `.stat-grid` 是 `repeat(6, minmax(0,1fr))`，单卡 **169.3px**；扣掉 `padding 16px 18px`×2 + 图标 38px + `gap 14px` 后，`.j-stat-text` 可用宽仅 **81.3px**。`.j-stat-value` 是 `white-space: nowrap`，实测 `clientWidth`/`scrollWidth`：

| 方案 | 4 位 | 5 位 | 6 位 |
|---|---|---|---|
| **现状 24px** | 52/52 ✓ | 67/67 ✓ | 79/**82 溢出** |
| 报告建议 32px | 67/67 ✓ | 71/**86 溢出** | 71/**106 溢出** |
| 死代码原规格 32px/24px padding/44px icon | 57/**67 溢出** | 57/**86 溢出** | 57/**106 溢出** |
| 折中 28px | 60/60 ✓ | 71/**77 溢出** | 71/**94 溢出** |

- 溢出**只在 1440px 出现**（最紧布局）；1280px 单卡 301.3px、1024px 单卡 216px 各档位均不溢出。
- 现状 24px 的安全上限是 **5 位数字**；32px 只有 **4 位**。

### 问题本质

这是「视觉权重」与「数值位数余量」的取舍。统计数字是**会增长的量**（收藏数、便签数会变多），为字号牺牲位数余量是拿确定的稳健性换不确定的观感。

### 选项

**A. 维持 24px（推荐）**
- 理由：24px/800 相对标签 12px 已是 2 倍层级差，169px 卡片内视觉权重足够；保留 5 位余量。

**B. `font-size: clamp()` 自适应**
- 形态：如 `font-size: clamp(20px, 2.2cqi, 32px)` 配合容器查询，或按 `scrollWidth` 溢出时降档。
- 优点：大数字自动缩小，视觉上更大胆。
- 缺点：需要容器查询支持（或 JS 测量），复杂度上升；数字大小会随位数变化，同一排卡片数字不等高。

**C. 按位数降档**
- 形态：4 位用 32px、5 位用 28px、6 位用 24px。
- 优点：兼顾。
- 缺点：同排数字字号不一致，视觉上更乱。

**D. 改网格列数**
- 形态：1440px 下从 6 列改 4 列或 5 列，单卡变宽，就能安全用 32px。
- 优点：同时解决字号与拥挤。
- 缺点：6 张卡变 4 列会换行（4+2），或需要重新设计排布。

### 我的判断

推荐 **A**。若你确实觉得统计数字应该更醒目，推荐 **D**（改列数）而不是 B/C —— D 是唯一「既放大又不牺牲余量」的选项，代价只是排布从一行 6 张变成两行。

### 实施中发现并修复的回归（重要教训）

按上述决策改完后出现**整页白屏**：进入概览/回收站正常，离开时 `#app` 塌成空壳。

**根因**：为解释 `active-module` 只是占位，我在 `OverviewLayout.vue` / `RecycleLayout.vue` 的 `<template>` **根层级**加了 HTML 注释。Vue 3 会把 HTML 注释编译成真实节点，组件因此从「单根」变成「多根 Fragment」；而 `App.vue` 用 `<Transition name="page-fade" mode="out-in">` 包裹路由组件 —— `<Transition>` 只能作用于单根，多根会让 `out-in` 状态机卡死（旧组件已卸载、新组件永不挂载）。

**约定（后续所有改动遵守）**：
- **不要在 SFC 的 `<template>` 根层级写 HTML 注释。** 模板相关的说明写进 `<script setup>` 的 JSDoc，或放到根元素**内部**。
- 判断方法：看 dev server 编译产物里是否出现 `DEV_ROOT_FRAGMENT`，或根节点是否为 `_createElementBlock(_Fragment, …)`。
- 这条约束在 `OverviewLayout.vue`、`RecycleLayout.vue`、`SideNav.vue` 三处已写成注释留档。

**定位方法（可复用）**：`git stash push -u -- <path>` 回到基线复现同一操作序列 —— 若基线正常，即可判定为本次改动引入的回归，而非既有缺陷。本次正是靠这一步把排查范围从「整个路由/过渡机制」收缩到「本批 diff」。
