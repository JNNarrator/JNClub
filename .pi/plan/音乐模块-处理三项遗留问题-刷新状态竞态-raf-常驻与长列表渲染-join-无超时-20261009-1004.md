## 改动 1：刷新缓存的状态竞态

**问题**：`TrackCacheService.manualRefresh()` 标了 `@Async`，Controller 返回时后台线程可能还没执行到 `refreshAll` 的 `refreshing = true`；若此时恰好有 `scheduledRefresh` 在跑，`refreshAll` 开头的 `if (refreshing) return` 会让本次调用**直接返回**。前端 `TrackList.vue:40-53` 在 POST 成功后 1.5s 就开始轮询，首次就可能读到 `inProgress=false` → 立即判定「刷新完成」并 `clearInterval`，而后台其实还在续期或根本没跑。

**后端** `jnclub-module-music/.../track/service/TrackCacheService.java`

1. 把「对外状态」与「执行互斥」分开：
   - `private volatile boolean refreshing` —— 语义改为「已抢占本轮名额（排队或执行中）」，供 `/cache/status` 使用。
   - 新增 `private boolean beginRound()` / `endRound()`（`synchronized` + `volatile`），保证抢占与可见性。
2. 新增 `roundExecutor`（**单线程**守护线程池）。原因：`refreshExecutor` 只有 4 线程且要跑 `refreshOne`，若「轮次调度」也占用它，会形成「任务占线程 → 内部再向同一池提交 → join 等待」的脆弱结构（并发度降到 1 就会死锁）。调度与取链分池，彻底消除该风险。
3. 三个入口统一为「同步抢占 → 提交到 roundExecutor → finally 释放」：
   - `manualRefresh()`：**去掉 `@Async`**，改为 `if (!beginRound()) return false;` 同步置位后提交，返回 `boolean` 供 Controller 区分「已触发 / 已有任务在执行」。
   - `scheduledRefresh()`：先 `beginRound()`，成功才提交任务（Redis 锁逻辑移入任务内），不再占用 `@Scheduled` 的调度线程。
   - `onStartup()`：把裸 `new Thread` 换成 `roundExecutor.execute(...)`；`initCache()` 去掉无效的 `@Async`（它是同类内部调用，注解本就不生效）。
4. `refreshAll()` 移除自身的 `if (refreshing) return` 置位逻辑（互斥已由 `beginRound` 承担）。
5. 清理 `TrackCacheService` 里重复的 `import java.util.concurrent.atomic.AtomicInteger;`（我上一轮引入）。
6. 移除 `MusicModuleConfig` 的 `@EnableAsync`：已 grep 确认全项目仅这两处 `@Async` 且都被移除，无其他消费者；同步更新该文件的类注释。
7. `AdminLanzouController.refreshCache()` 改为返回明确结果（`已触发` / `已有刷新任务在执行`）。

**前端** `music-frontend/src/components/TrackList.vue`

- 轮询收敛条件加双保险：必须**至少见过一次 `inProgress=true`**，或轮询次数达到宽限上限（4 次 ≈ 6s）才允许结束；否则继续轮询，避免「触发即完成」的假象。
- 轮询加总超时兜底（如 10 分钟），超时后停止并提示，防止后台卡住时无限轮询。
- `total === 0` 时按钮显示「准备中…」而非 `0/0`。

## 改动 2：PlayerPage 的 rAF 常驻

**问题**：`PlayerPage.vue` 的 `syncLyrics` 循环在 `isPlaying` 期间以 60fps 常驻。上一轮我已把「播放页关闭」时的**计算**降到 20Hz，但循环本身仍在每帧空转（`PlayerPage` 在 `App.vue` 常驻，不随页面切换卸载）。

**前端** `music-frontend/src/components/PlayerPage.vue`

- 把 `syncLyrics` 拆成 `updateLineState(now, allowScroll)` + `rafLoop()`。
- `startRaf()` / `stopRaf()` 幂等（用 `rafId` 判断，避免重复启动）。
- 启停条件改为 `isPlaying && ui.showPlayerPage`：
  - 播放页打开 → rAF 驱动（行内进度条需要平滑）。
  - 播放页关闭 → **完全停掉 rAF**。
- 播放页关闭时用 `watch(() => player.currentTime)` 驱动 `updateLineState(..., false)`：`currentTime` 由 `timeupdate` 事件更新（约 4Hz），足够刷新 `currentLineIdx` 与 `document.title`。
- 保留 `onUnmounted` 清理。

## 改动 3：TrackList 长列表渲染

**问题**：`tracks` 数组与 DOM 只增不减（每页 20 条，无限滚动 `push`），滚动容器内节点数无上界。

**采用低风险方案（CSS 层）** `music-frontend/src/components/TrackList.vue`：

```css
.track-rows .row {
  content-visibility: auto;
  contain-intrinsic-size: auto 61px;
}
```

- 浏览器跳过屏外行的渲染/布局/绘制，DOM 结构与 `scrollHeight` 语义不变 → **不影响无限滚动与 pull-to-refresh 的判定逻辑**（这是选它而非虚拟滚动的主因）。
- `contain-intrinsic-size` 用 `auto` 关键字：首次估算 61px，之后浏览器按实测值记忆，因此能自适应桌面/移动端不同行高（`.row` 在移动端 padding 与字号都更小）。
- 老浏览器（iOS Safari < 18）不支持时自动降级为普通渲染，无副作用。

## 改动 4：`join()` 无超时

**问题**：两处 `CompletableFuture.join()` 无上限，单个任务卡住会无限阻塞调用线程。

**后端** `jnclub-module-music/.../track/service/impl/TrackServiceImpl.java`

- `loadSongFoldersRecursively` 的 `fu.join()` 改为带预算的 `get(timeout)`：
  - 新增 `FOLDER_SCAN_TOTAL_TIMEOUT_MS = 120_000`（整轮总预算）与 `FOLDER_SCAN_LEVEL_TIMEOUT_MS = 60_000`（单层预算），每层取 `min(单层预算, 剩余总预算)`。
  - 依据：单次 `listFiles` 含 2 次 `douploadPost`，每次最多 3 次反爬重试（各 sleep 800ms/2000ms）+ OkHttp 读超时 30s，最坏约 90s；正常仅 1~3s。故 60s/层、120s/轮 远高于正常值，又能给出上界。
  - `TimeoutException` → 归入「扫描失败」路径：**返回空列表、不写缓存、进入已有的 30s 冷却**（复用上一轮的 `folderScanBlockedUntil`）。
  - **关键约束**：超时绝不缓存部分结果——否则曲库会以不完整状态被缓存 45 分钟。
  - `InterruptedException` 恢复中断标志后同样走失败路径；`ExecutionException` 解包后按既有逻辑判定 `LanzouSessionException`。

**后端** `TrackCacheService.refreshAll`

- `allOf(...).join()` 改为 `get(timeout)`，超时值 = `min(20min, max(60s, ceil(ids.size() / REFRESH_CONCURRENCY) × 60s))`。
- 超时只记 `warn` 并正常结束本轮：已完成的结果都已落库；未完成的曲目在下一轮 `selectDueForRefresh` 中仍会被挑出（判定依据是「余量不足」，不是「本轮跑过」），因此**天然可恢复，无数据丢失**。
