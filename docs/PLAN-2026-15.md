# JNClub 功能规划 · 2026-15（日历 2.0 + 搜索体验增强 + 稳定与性能）

> 状态：✅ 已全部实现（后端/前端构建通过）
> 来源：PLAN-2026-14 交付后，用户选择的三条迭代线：**日历 2.0（M2）**、**搜索体验增强（M4）**、**稳定与性能收尾**。
> 策略：三条线相互独立；建议按「日历 2.0 → 搜索体验 → 稳定与性能」的顺序实施。
> 目标：
> - 日历补齐「周视图 / 时间段 / 拖拽交互 / 自然语言添加」，让 M1 数据模型真正形成闭环。
> - 搜索补齐「语法过滤 / 服务端历史 / 建议词 / 结果深链」，让已有搜索源更好用。
> - 稳定与性能做一轮低成本治理，降低数据增长后的卡顿和风险。

---

## 一、现状核实（基于当前代码）

### 1. 日历 2.0 前置

- `CalendarService.month()` 只支持月视图聚合；返回的 `todo` 仅含 `id/title/note/priority/completed/dueDate/completedAt`，**未包含** M1 已落地的 `dueTime / remindAt / recurrence / itemCount / itemCompletedCount`。
- `CalendarView.vue` 目前只有月网格，支持：点击空白格新建、待办拖拽改期、勾选完成、删除、便签入口。
- `TodoService` 已有 `dueTime / remindAt / recurrence / recurrenceInterval` 字段与「重复待办完成后自动推进」逻辑，但日历查询不会把重复待办展开到未来日期，周视图也需要新 API。
- 快速添加仍只有「标题 + 优先级 + 日期」，没有 `dueTime / remindAt / recurrence`，也没有自然语言解析。

### 2. 搜索体验增强（M4）前置

- `SearchService` 已覆盖 10 个分组：收藏 / 便签 / 云盘 / 密码库 / 标签 / 音乐 / 待办 / 稍后读 / 订阅源 / 文章。
- `SearchDrawer.vue` 已有防抖搜索、类型筛选 Chips、本地 localStorage 历史、快捷命令、键盘导航、结果直达（打开 URL / 下载文件 / 打开便签）。
- 仍缺：
  - `type:` / `date:` / `#标签` 搜索语法解析与可视化 Chips。
  - 服务端搜索历史（当前仅 localStorage，换设备不同步，无法统一清理）。
  - 搜索建议接口（`/api/search/suggest`）。
  - 结果深链：待办 / RSS 文章目前只跳到模块首页，不能定位到具体记录。

### 3. 稳定与性能可优化点

- 搜索为多张表顺序查询，每张表 `LIMIT 20~50`；数据量大时缺少索引保障。
- `GET /api/todos` 当前一次性返回全部待办；记录多时响应体与前端渲染压力上升。
- `t_notification`、`t_search_history` 等增长型表缺少数量上限/清理策略。
- 前端构建已做 `manualChunks` 与路由懒加载，但大包 `naive-ui`、`md-editor` 仍有优化空间（如首屏只加载必要组件、编辑器资源按需）。
- 部分列表接口没有 `page/pageSize` 维度，无法做“加载更多 / 虚拟滚动”的渐进增强。

## 二、A. 日历 2.0（推荐先做）

### A1. 日历数据接口增强

**后端**
- `CalendarService.todoView()` 补全返回字段：
  ```json
  {
    "id": 1,
    "title": "...",
    "note": "...",
    "priority": 0,
    "completed": 0,
    "dueDate": "2026-08-01",
    "dueTime": "09:00:00",
    "remindAt": "2026-08-01 08:30:00",
    "recurrence": "WEEKLY",
    "recurrenceInterval": 1,
    "itemCount": 3,
    "itemCompletedCount": 1
  }
  ```
- 新增 `GET /api/calendar/range?start=YYYY-MM-DD&end=YYYY-MM-DD`：
  - 返回 `{ todos, notes, days }`，`days` 按天生成数组，前端可直接渲染周/月视图。
  - 待办查询包含：
    - 落在区间内的普通待办；
    - 跨区间逾期未完成待办（折叠到 start 之前的 `overdue` 桶）；
    - **重复待办动态展开**：根据 `recurrence / recurrenceInterval / dueDate / dueTime` 生成区间内的所有实例，不落库、不改原记录。
  - 便签沿用“更新时间落在区间内”的聚合逻辑。
- `month` 接口改为内部调用 `range`，保持前端兼容。

**表结构**
- 本阶段不需要新增字段；如需 `end_time`（结束时间）做日程块，可迭代：先支持 `dueTime` 作为开始时间，结束时间用可选 `endTime` 字段（`t_todo` 增加一笔幂等迁移）。
- 决策：第一版先做 **单点/时间段事件**，以 `dueDate + dueTime` 展示；不做复杂跨日事件。

### A2. 周视图与时间网格

**前端 `CalendarView.vue`**
- 顶部新增视图切换：`月 / 周`（`NRadioGroup` 或 Segmented）。
- 月视图保留现有交互，但待办卡显示 `HH:mm`、重复图标、子任务进度。
- 新增周视图：
  - 列：周一～周日；行：时间轴（如 00:00–23:00，粒度 1 小时）。
  - 有 `dueTime` 的待办按 `dueDate + dueTime` 定位在对应时间格。
  - 无 `dueTime` 的待办放在列顶部“全天”区域。
  - 显示重复实例；点击可勾选完成/删除。
- 周视图拖拽：
  - 拖到某天某时间格 → `PUT /api/todos/{id}` 更新 `dueDate + dueTime`。
  - 若从全天区拖到时间格，只设置日期，不强制补时间？**决策：拖到时间格默认补 `09:00`**；拖到全天区则只更新日期。
- 移动端周视图保持可横向/纵向滚动，时间格最小高度适配触控。

### A3. 自然语言快速添加

- 在 `CalendarView` 与 `TodoView` 的快速添加框支持自然语言解析：
  - `周五 14:00 准备周报`
  - `每天 9:00 站会`
  - `本周日 晚上 整理发票`
  - `明天 10:30 提醒 15 分钟前 提交材料`
- 解析器位置：新增 `src/shared/utils/todoNlp.ts`（纯前端规则解析，不引第三方 NLP）。
- 解析成功 → 自动填入 `title / dueDate / dueTime / remindAt / priority / recurrence`；失败 → 退化为普通标题。
- 后端无需新接口，继续走 `POST /api/todos`。

### A4. 日历与待办联动

- 周视图/月视图的待办卡增加“编辑”入口（打开编辑弹窗，字段与 M1 待办编辑一致）。
- `/todos?highlight=123` 与 `/calendar?date=YYYY-MM-DD&todo=123` 互相跳转定位。

## 三、B. 搜索体验增强（M4）

### B1. 搜索语法解析

**后端 `SearchService`**
- 关键词解析（在 Service 入口拆分）：
  - `type:todo` / `type:note` / `type:bookmark` / `type:file` / `type:vault` / `type:feed` / `type:track` / `type:readLater` / `type:feedItem`
  - `date:today` / `date:week` / `date:month` / `date:YYYY-MM`
  - `#标签名` → 仅搜标签，或作为收藏/便签过滤条件（先支持标签分组精确定位）
- 返回额外字段 `parsed`：
  ```json
  {
    "keyword": "type:todo 报告",
    "cleanKeyword": "报告",
    "type": "todo",
    "date": "week",
    "tag": ""
  }
  ```
- 前端用 `parsed` 渲染可清除的语法 Chips；保留现有类型筛选 Chips 作为叠加过滤。

### B2. 服务端搜索历史

- 新增表 `t_search_history`（`id / user_id / keyword / create_time`，幂等建表）。
- 新增接口：
  - `GET /api/search/history`：最近 20 条
  - `POST /api/search/history`：记录关键词（可在前端搜索成功时调用；后端去重 + 最多保留 50 条/用户）
  - `DELETE /api/search/history`：清空
- `SearchDrawer`：
  - 空输入默认展示**服务端历史 + 本地最近命令**；历史来源优先服务端，接口失败降级 localStorage。
  - 保留本地最近命令（命令使用偏好不上服务端）。

### B3. 搜索建议

- 新增 `GET /api/search/suggest?keyword=X`：
  - 返回 `{ history[], commands[], groups[] }`
  - `history`：匹配用户历史
  - `commands`：前端可用但由服务端提示完整命令列表（也可前端本地）
  - `groups`：提示可搜类型（如“待办 / RSS 文章”）
- 前端在输入框聚焦且未提交时展示建议，点击建议直接搜索或插入输入框。

### B4. 结果深链

- 待办：`/todos?highlight=123`，TodoView 读取 query 后滚动到该待办并高亮/展开。
- RSS 文章：`/feeds?feedId=1&itemId=2`，FeedsView 切换到对应订阅并选中文章。
- 稍后读/收藏：已支持 `openUrl`，保留。
- 云盘：已支持下载，保留；后续可加“在云盘目录中定位”。
- 密码库：继续跳到目录（不能深链到解密条目，安全边界）。

### B5. 搜索交互细节

- `Tab` 键切换分组（当前已支持部分键盘；本阶段补 Tab 分组循环）。
- 结果行显示更多元信息：待办截止/重复/进度、RSS 发布时间/未读状态。
- 输入框 placeholder 更新为支持语法的提示文案。
- 搜索无结果时展示“尝试 `type:todo` / `#标签` 语法”提示。

## 四、C. 稳定与性能收尾

### C1. 数据库索引与迁移

- 在现有幂等初始化器（`TodoTableInit` 或统一 `SchemaInit`）中补充索引：
  - `t_todo(user_id, deleted, due_date)`、`t_todo(user_id, deleted, completed)`
  - `t_bookmark(user_id, deleted, read_later, read_at)`
  - `t_feed_item(user_id, title)` / `(user_id, feed_id, published_at)`
  - `t_notification(user_id, read_flag, create_time)`
  - `t_search_history(user_id, create_time)`
- 索引创建使用 `information_schema.STATISTICS` 幂等判断，不中断现有数据。

### C2. 列表接口分页收口

- `GET /api/todos`：
  - 保持默认返回全部（兼容现有前端），新增可选 `page/pageSize`；传 `page=1&pageSize=50` 时返回 `{ records, total, page, size }`。
  - 前端 TodoView 先保持现状，后续数据量大时再切“加载更多”。
- `GET /api/notifications`：已有 `limit`；补 `offset` 或 `page`，并限制单次最大 100。
- `GET /api/search`：保留每组 `limit`，新增每组 `total`（可选，避免每次全量 count 影响性能）。

### C3. 搜索性能优化

- 对高频字段改用前缀匹配优先：标题命中 `LIKE 'kw%'` 与包含匹配 `LIKE '%kw%'` 合并评分；不改变现有接口结构。
- 可选：对 `t_feed_item` 只搜最近 90 天或未读，减少扫描量（已在 PLAN-2026-14 规划中，作为可选项）。
- 必要时对单次搜索加 500ms 内存缓存（同一用户同一关键词短时间重复搜索直接返回）。

### C4. 前端性能与稳定性

- 引入 `JVirtualList` 或复用现有虚拟滚动：
  - 云盘文件、便签列表、RSS 文章列表在超过 100 条时启用。
- 图片/图标懒加载复查：
  - 收藏 favicon 已有 onerror 兜底；补 `loading="lazy"`。
- 通知轮询收敛：
  - 当前 AppHeader 60s 轮询；页面不可见时暂停，`visibilitychange` 恢复。
- 构建优化：
  - 保留 manualChunks；如发现 `naive-ui` 首屏过大，可评估按需引入或继续使用现有整包策略。
- 错误监控：
  - 在 `axios` 拦截器统一上报前端错误到 `console/后端错误日志接口`（可选，不新增第三方）。

### C5. 数据清理策略

- 搜索历史：每用户最多 50 条，超出删除最旧。
- 通知：默认保留最近 200 条，超出后定时清理（可放进 `ReminderService` 或独立 `CleanupService`）。
- 回收站已有每日清理，保留不动。

## 六、风险与边界

1. **重复待办展开**：动态展开不落库，但要做“完成实例”宇宙一致性设计：点击展开实例完成时，应调用现有 `PUT /api/todos/{id}/complete` 推进原待办，再刷新视图；避免出现“每实例独立 ID”的歧义。
2. **自然语言解析**：只做中文日期/时间规则版，识别不了就退化为标题，不阻塞主流程。
3. **周视图复杂度**：时间网格在移动端体验有限，先保证桌面端完整，移动端可读可点即可。
4. **搜索语法兼容**：现有普通关键词搜索行为不变；只有带 `type:` / `date:` / `#` 时才启用过滤。
5. **历史服务端化**：迁移 localStorage → 服务端时保留降级路径，避免老用户空历史。
6. **分页兼容**：所有新增分页参数均为可选，默认响应结构不变，避免前端一次性回归。
7. **索引开销**：新增索引仅覆盖高频查询列，避免过度索引影响写入。
